# Command Orbit: автоматическая синхронизация

## Рекомендуемый вариант: фоновая синхронизация при активности

Клиент хранит SQLite или browser storage как рабочую базу. После локального изменения он отмечает данные как `dirty`, ждёт 45 секунд без новых изменений и синхронизируется, только если приложение открыто, есть сеть и Google уже авторизован.

- Pull при запуске/возврате приложения и не чаще одного раза в 5 минут.
- Push через 45 секунд после последнего локального изменения.
- Повтор с интервалами 1, 5 и 15 минут, только пока приложение активно.
- Ручные кнопки «Сравнить», «Загрузить» и «Отправить» остаются.
- Google Sheets API вызывается только при реальной необходимости, поэтому вариант почти не создаёт инфраструктурных расходов.

Это лучший баланс для небольшой CRM: изменения появляются на других устройствах достаточно быстро, а отдельный сервер, push-канал и постоянный polling не нужны.

## Другие варианты

### Экономный периодический

Pull при запуске и каждые 15 минут, push при уходе приложения в фон или по ручной команде. Минимум запросов, но пользователь может видеть устаревшие данные до 15 минут.

### Почти реальное время

Backend принимает изменения, использует Google Drive/Sheets notifications и рассылает события устройствам. Задержка минимальна и возможна строгая атомарность, но появляются постоянно работающий сервис, база операций, мониторинг и расходы. Для текущего масштаба не рекомендуется.

## Разрешение конфликтов

Текущий снимок предотвращает обычную перезапись через проверку версии, но для автоматического режима нужен merge на уровне записей:

1. Каждая сущность получает `UpdatedAt`, `UpdatedByDevice` и номер ревизии.
2. Удаления сохраняются как tombstone, иначе удалённая запись вернётся с другого устройства.
3. Изменения разных записей объединяются автоматически.
4. Для одной записи объединяются независимые поля, если менялись разные поля.
5. Если одно поле изменено на двух устройствах, синхронизация останавливает только эту запись и показывает сравнение «локально / Google» с выбором значения.
6. Остатки, резервы, платежи и приёмки не перезаписываются как итоговое число: они синхронизируются как неизменяемые операции. Это исключает потерю движения склада или денег.

## Этапы внедрения

1. Добавить журнал локальных изменений и идентификатор устройства.
2. Перейти со снимка на операции для склада, продаж и платежей.
3. Добавить merge обычных карточек и UI конфликтов.
4. Включить foreground-таймер и debounce push.
5. Только после накопления метрик решать, нужен ли backend real-time.
